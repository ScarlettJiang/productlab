**决策：保留 v2 为离线回归基线；不批准自动处理上线，也不批准据此投入微调。**

32 条合成诊断案例中，完整成功从 17/32 到 24/32；不当自动路由从 10 到 3；不必要澄清从 0 到 2。安全升级切片仍 0/3。净提升存在，但分布不代表用户流量，且测试集可见，无法换算业务收益。

## 为什么不直接“换个更大模型”

当前没有任何 LLM 运行结果，无法归因到模型能力。即使以后真实模型分类正确，也可能因为工作流缺少风险规则而执行错误动作。先定义允许做什么、何时交人，再判断模型是否理解了输入。

真实模型下一阶段比较时：固定同一 rubric、同一冻结评测集、同一输出合同；先比较规则 v2 与模型原始输出，再比较加相同安全门控的端到端结果。两层指标分开，避免把工作流的贡献算给模型。只有在标签复核、提示词/上下文/输出约束验证后，真实模型仍稳定失败，才考虑模型替换或训练。本阶段这些都是待验证方案，不是结论。

## 第一阶段验收与边界

已完成：32 条数据、明确 rubric、严格评分器、v1/v2 真实执行、逐例错误和成对对照、运行哈希、6 项自动测试与外部预测接口 smoke test。

仅作为下一阶段候选的临时门槛：格式完整、已知安全案例无漏接管、正常任务无新增失败，且人工复核澄清成本。它们是设计要求，不是已满足的上线标准；实际部署还需更多独立样本与业务容错预算。

这里展示的是 **Evals 设计 → 执行 → 定位 → 工作流干预 → 复测 → 有边界的产品决定**。尚未证明 LLM 调优能力、完整 Agent 工具使用能力或线上商业结果。

对招聘经理的准确表述：“构建并运行了一个 32 案例的合成工单决策评测，建立规则基线与不确定性门控对照；完整决策正确率从 53.125% 到 75%，同时发现否定表达的澄清副作用与安全接管缺口。结果仅适用于该诊断集。” 面试前应亲自重跑、复核争议标签并能解释代码；不要将 AI 助手完成的实现说成自己独立编写。
