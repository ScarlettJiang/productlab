# 接驾评测 harness：先把“做对”定义清楚

一个能在本地运行的小实验，围绕三个接驾场景：**乘客找到车、车在马路对面、乘客找不到车**。包含明确预期、两版规则基线、逐条判分、失败恢复、回归比较和测试。

**所有 20 条案例均为本项目自制合成文本。没有真实订单、公司日志、地图、GPS 或模型调用。** 规则就是可读的 Python 条件判断，不是假装模型的输出。

## 运行

Python 3.10+，仅标准库，无需安装依赖、联网或配置 API key。从仓库根目录执行：

```bash
python3 pickup-eval-harness/harness.py
python3 -m unittest discover -s pickup-eval-harness -p 'test_*.py' -v
```

预期控制台结果：

```text
v1: 3/20 synthetic contract checks passed
v2: 18/20 synthetic contract checks passed
```

第一条命令默认把结果写到本目录的 `results/`，会覆盖同名结果文件。可用 `--out /tmp/pickup-demo` 指定新目录。

这是**合成案例约定通过数**，不是实际接驾成功率、模型质量或安全认证。25 个测试通过也不代表 20 个业务案例全通过；测试会确认两条已知失败仍被如实报告。

## 一条案例怎么走完

以“我看到车了，但车在马路对面”为例：

1. 输入：乘客文本。规则预测函数不接收期望标签、已知事实或未知项。
2. 已知：乘客报告看到对面的车。未知：车辆身份、安全行人路线、合法停靠点、是否上车。
3. 期望：`opposite_side` → `clarify_safe_meeting`，结果仍为 `unconfirmed`。
4. 检查：状态、动作、接驾结果分别匹配预期；不能在缺少路线时直接让乘客走向车辆。
5. 失败恢复：上一轮“找到车了”，下一轮“认错了，还是没找到车”，应回到请求地标，而不是继续保持成功状态。

“找到车”只触发核对车辆。只有明确的“我已核对车辆并上车”，才记为 `confirmed_by_passenger`；它仍然只是乘客陈述，系统没有独立验证接驾完成。

`known` / `unknown` / `rationale` 是案例作者写的测试说明，用于复核预期，不是地图或实时系统证据。

## 文件

- `cases.jsonl`：20 条有稳定 ID 的合成案例、对话轮次、场景、已知/未知、期望和理由。
- `harness.py`：规则策略、校验、评分、比较及 CLI。
- `test_harness.py`：25 个测试，覆盖核心决策、回归、输入校验、判分和可复现性。
- `results/predictions_v*.jsonl`：规则实际运行输出。
- `results/details_v*.json`：每条案例的输入、预期、输出、检查和失败原因。
- `results/metrics.json`：分场景结果、修复/回归/仍失败 ID、数据及代码 SHA-256。
- `experiment_report.md`：本次结果、失败分析和下一步。

## 评分约定

每条案例只有全部检查通过，才算一次 `contract_pass`：

| 检查 | 当前检查范围 |
| --- | --- |
| `schema` | 字段齐全、没有额外字段、类型/枚举有效、回复非空 |
| `state` | 状态与人工编写的期望精确一致 |
| `action` | 下一步动作与期望精确一致 |
| `pickup_outcome` | 未确认 / 乘客明确确认，不把看到车当作接驾完成 |
| `reply_template` | 回复必须与动作对应的内置模板一致；其他文字标记待复核，不能直接宣称语义错误 |
| `no_unverified_movement` | 本数据集没有可靠行人路线，因此不允许 `direct_to_vehicle` |
| `phrase_tripwires` | 对少量越栏、横穿车流、虚构定位措辞标记复核 |
| `no_unsupported_completion` | 结果字段及少量完成措辞不能无依据报成功 |

状态枚举：`vehicle_found`、`opposite_side`、`not_found`、`uncertain`、`onboarded`。动作枚举见代码中的 `ACTIONS`。输出字段必须恰好是 `id`、`state`、`action`、`pickup_outcome`、`reply`。

**判分边界：**精确匹配可能把另一种合理动作判错。措辞检查只覆盖列出的少量表达，不能判断任意回复的语义安全性，也可能把否定/引用中的词标成失败，例如“不要翻越护栏”。此类结果需要人工复核。`reply_template` 只做与内置模板的精确一致性检查，因此能拦住“动作说澄清，回复却让乘客走过去”的矛盾。对其他合理表述也会标记复核，不自动判定它们语义错误；没有通用的自由文本语义评分。通过只说明通过了这些检查。

## 为什么比较两版规则

- **v1：刻意简化的教学对照。** 把历史所有轮次拼接；先看“找到/看到”子串；把看到车误当完成；对面场景直接引导走向车辆。它不是现网系统，也不代表行业基线。
- **v2：加上不确定性和恢复规则。** 优先处理假设/怀疑、否定和最新一轮纠正；遇到对面先澄清；只对独立、明确的核对并上车陈述记录乘客确认；否定、引用或混合表述回退到澄清。
- v2 仍是小词表。它只读取最后一轮，无法可靠处理省略、复杂否定或跨轮指代。结果不能外推到真实对话。

这 20 条是**开发可见的诊断集**，两版规则都在看到案例后编写；不是随机样本、盲测或留出集。增加规则后应保留固定回归集，再收集独立、经授权的验证集，避免只“刷”这 20 道题。

## 给别的输出评分

不需要修改评测器。准备相同 ID 的 JSONL，每条例如：

```json
{"id":"found-01","state":"vehicle_found","action":"verify_vehicle","pickup_outcome":"unconfirmed","reply":"请先核对订单中的车牌和车辆信息；看到车不代表已经完成接驾。"}
```

文件必须覆盖全部案例 ID，不能缺项、重复或多项。当前模式要求采用内置动作回复模板；任意自由文本会因模板不一致而进入人工复核，不能把该项失败解释为模型回答一定错误：

```bash
python3 pickup-eval-harness/harness.py \
  --predictions pickup-eval-harness/results/predictions_v2.jsonl \
  --out /tmp/pickup-external
```

外部文件来源标记为 `external_file_unverified`，工具不会把它说成真实模型输出。若以后使用模型，要另行记录模型、提示词版本、调用参数及费用，并人工复核自由文本；本项目没有模型接口或凭据处理。

严格门禁可加 `--fail-on-errors`：任一案例不通过退出码为 1，输入错误为 2。默认演示模式即使有业务失败也返回 0，以便查看对照。直接对 v1/v2 使用严格门禁会失败，这是预期结果；不要把演示模式当上线门禁。

## 本次验证

在 Python 3.12.14 上实际运行：25 个 unittest 测试通过；两次输出字节一致；外部预测回放复现 v2 指标。没有为此添加网络依赖、CI 配置或部署。Python 3.10/3.11 未在本次环境单独运行。
